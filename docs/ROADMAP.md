# Novel Studio 开发路线图

本文档基于当前代码真实状态重排版本计划，避免“文档仍在 v0.1，代码已经进入下一阶段”的漂移。

更新日期：2026-03-25

---

## 当前阶段判断

### 结论

项目当前最准确的定位是：

**核心创作引擎已经成型，下一阶段的主任务是系统集成与产品化，而不是继续扩展零散功能点。**

### 已经具备的能力

- `outlines`：Bible、Substory、Chapter Blueprint、Scene 生成能力已经存在。
- `materials`：文本分段、素材提取、结构化结果输出已经存在。
- `writing`：按 scene 逐段生成正文，并能接收 materials、前文和 summary 上下文。
- `post_writing`：章节总结与卷内累计总结已经有独立引擎实现。
- `db` / `models`：SQLite 和 ChromaDB 的本地存储基础已经存在。
- `tests`：核心模块已有较完整 unit/integration 测试。

### 当前真正的短板

- 缺少统一的应用级 workflow / orchestrator。
- Service 层只有 `materials` 有初步实现，其余关键 Service 仍未落地。
- `main.py` 仍是占位入口，API 层尚未建立。
- 文档存在明显过期，尤其是测试文档和项目状态说明。
- 测试虽然能跑，但调试模式、受限环境运行方式、Service 层覆盖都还不够清晰。

### 战略判断

接下来 6 到 8 周，最重要的目标不是“多做几个 AI 功能”，而是：

1. 把现有能力串成一个稳定闭环。
2. 让系统具备明确的状态流转和对外接口。
3. 让测试、文档和代码重新同步。

## 阶段 1：创作闭环收口

**目标**：从“模块可跑”升级为“一个章节创作任务可稳定执行、保存、回溯”。

**建议周期**：2 到 4 周

### 核心任务

- 定义统一编排流程：
  `Bible -> Substory -> Chapter Blueprint -> Chapter -> Writing -> Post-Writing -> Persistence`
- 为 `outlines`、`writing`、`post_writing` 补齐 Service 层。
- 明确每个阶段的输入、输出和持久化对象。
- 把章节总结、卷内累计总结接入主 workflow，而不是停留在独立引擎。
- 设计错误边界：
  LLM 失败、结构化解析失败、向量写入失败、上下文过长时的处理策略。

### 交付标准

- 能从单一入口触发完整章节创作。
- 每个阶段结果都可以被保存、复查和复用。
- 章节生成完成后，summary 和关键状态可继续为下一章提供上下文。

### 这一阶段不要做的事

- 不要先做前端精修。
- 不要先做多用户和权限。
- 不要先做复杂评估系统。

## 阶段 2：工程反馈系统稳定化

**目标**：让测试、文档、调试路径真正成为开发加速器，而不是表面覆盖。

**建议周期**：1 到 2 周，可与阶段 1 并行推进

### 核心任务

- 维护分层测试入口：
  `test`、`test-quick`、`test-unit`、`test-integration`
- 为 Service 层补齐测试，尤其是 workflow 和持久化逻辑。
- 补 CI 配置，至少在 `develop` 上自动执行 lint、type-check、tests。
- 在测试文档中明确：
  并行模式、单进程调试模式、snapshot 维护模式、受限环境缓存配置。
- 清理明显过期文档。

### 当前状态记录

- 2026-03-25 在提权环境中执行 `uv run poe test`：
  `108 passed in 11.34s`
- 总覆盖率：
  `99.20%`
- 需要继续关注的空白：
  Service 层测试仍薄弱，应用入口和 API 还没有对应测试面。

## 阶段 3：API 与流式输出

**目标**：为前端和外部调用提供稳定边界，而不是直接暴露内部引擎对象。

**建议周期**：2 到 3 周

### 核心任务

- 选定并实现 API 框架，建议 FastAPI。
- 设计章节生成、素材导入、summary 查询等核心接口。
- 将写作链路改造成支持流式输出：
  优先考虑 SSE，其次 WebSocket。
- 为长任务增加任务状态、错误回传、取消能力。
- 输出 OpenAPI 文档。

### 交付标准

- 前端不需要直接理解内部 engine/context，即可调用主要创作流程。
- 章节生成支持流式回传文本。
- API 错误结构稳定，便于 UI 和日志系统消费。

---

## 阶段 4：前端 MVP

**目标**：验证产品闭环，不追求精修 UI。

**建议周期**：2 到 4 周

### 核心任务

- 完成最小可用页面：
  Bible 管理、Substory 列表、章节生成页面、summary 查看。
- 接入流式写作显示。
- 提供基础项目状态展示：
  当前卷、当前章、最近 summary、生成日志。
- 做到移动端可用，但不提前投入复杂视觉打磨。

### 产品原则

- 先把“创作过程可见、可控、可回退”做出来。
- 不要在 API 未稳定前过度设计状态管理和交互细节。

---

## 阶段 5：评估与持续优化

**目标**：建立质量闭环，让 Prompt 和流程优化不再依赖纯人工试错。

**建议周期**：2 到 4 周

### 核心任务

- 增加 LLM-as-a-Judge 评估器。
- 定义评估维度：
  情节连贯性、人物一致性、情绪表达、文风稳定性。
- 为 Prompt、模型、生成结果建立可追踪版本关系。
- 引入 A/B Testing 或离线评估批处理。
- 让评估结果反哺 Prompt 和后处理模块。

### 进入本阶段的前提

- 主 workflow 已稳定。
- API 已固定主要输入输出。
- 测试和文档同步机制已建立。

---

## 暂缓事项

以下方向有价值，但不应进入最近两个迭代的主线：

- 多用户与权限系统
- 插件化架构
- 多版本生成投票
- 多模态能力
- 协同创作系统
- 复杂世界观可视化编辑器

这些功能会放大系统复杂度，应该建立在稳定编排层和 API 边界之后。
